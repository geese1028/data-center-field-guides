# 16. 診断事例集：アルゴリズムによる検知ヒットの対処法

前章で解説した変化点検知アルゴリズムは、タイムスタンプを出力する。この最終章では、アルゴリズムが検知ヒット（警報）を発行した際に、エンジニア、オペレーター、および第三者監査人が現場で物理的に何をすべきかについての実践的な診断事例集を提供する。

ここに提示するシナリオは、複数メガワット規模の高密度液冷施設における実際のコミッショニング試験から抽出された複合運用事例研究である。もしある事例が身に覚えのある居心地の悪さを感じさせるとすれば、それは負荷装置試験を拙速に進めようとする際に業界全体で繰り返し発生している典型的な障害モードだからである。

## 事例1：ヒットが指令されたステップと一致する場合

### 運用上の証拠
FocusまたはFLOCが `14:15:02 UTC` に警報をトリガーした。オペレーターのログにより、25%（30kW）から50%（60kW）への指令負荷ステップが `14:15:00 UTC` に開始されたことが確認される。有効電力は1.2秒以内にクリーンにステップ変化し、冷媒還流温度は滑らかな指数関数的上昇（τ ≈ 45 秒）を開始した。

### 診断上の判定
- **人間の分類**：**予期されたステップ（EXPECTED STEP）**。
- **取るべきアクション**：指令タイムスタンプと並べて監査ログにヒットを記録する（Δt = +2.0 秒、許容される5秒の制御遅延の範囲内）。
- **回避すべき落とし穴**：検出器が「過敏すぎる」と判断し、次のステップで沈黙するように検知閾値を引き上げてはならない！指令されたステップに対して沈黙することは、検出器が不感症（盲目）である証拠である。誠実なアルゴリズムであれば、指令された負荷ステップを検知して当然である。イベントをログに記録し、試験を続行せよ。

## 事例2：定常保持区間の内部で発生した指令外のヒット

### 運用上の証拠
100%負荷（120kW）での計画された15分間の定常保持時間に入って7分が経過した。指令有効電力には一切の変化がない。`14:37:18 UTC` において、FLOCが還流温度チャネル上で警報をトリガーした。

リアルタイムのデータブロックを精査したオペレーターは、以下を観測する：
- 有効電力は 120.1 kW で完全に一定を維持している。
- ラック2の体積流量が 176.4 LPM から 142.1 LPM へと下方にドリフトしている。
- ラック2の冷媒還流温度が 45.1°C から 48.9°C へと急上昇している（ΔT が10.0Kから13.8Kへと拡大）。

### 診断上の判定
- **人間の分類**：**指令外の保持途中破壊［水力異常］（UNCOMMANDED MID-HOLD BREAK [HYDRAULIC ANOMALY]）**。
- **物理的根本原因**：調整トリム弁のアクチュエータが流体圧力によってスリップしたか、インラインの50μmバイパスストレーナーに施工異物（切粉など）が詰まり始めたか、あるいはオペレーターが二次側マニホールドの手動ボール弁に誤って接触した。
- **取るべきアクション**：
 1. 48.0°Cを超える温度ドリフトで停止するという事前宣言済みの安全規則がある場合、直ちにヒーターをトリップさせる。
 2. トリップせずに運転が完了した場合、`14:37:18 UTC` において**保持区間を分割（SPLIT）**する。破壊前の最初の7分間は部分的な定常状態の証拠として成立し得る。しかし、後半の8分間は保持安定性基準において**不合格（FAIL）**となり、100%容量の検収サインに使用することはできない。
 3. 15分間の全ウィンドウを平均化して単一の人為的プラトーを作り出すことは断じて許されない！悪化した流量を直前の健全な流量と平均化することは、水力学的劣化を覆い隠す都合の良い虚構を捏造することにほかならない。

## 事例3：2つのオンライン検出器の意見が不一致の場合

### 運用上の証拠
15分間の保持時間中、FLOCが `15:10:14 UTC` に警報をトリガーした。Focusはその18秒後の `15:10:32 UTC` に警報をトリガーした。オペレーターの指令ログには何の記録もない。

### 診断上の判定
- **人間の分類**：**生散布データの点検（INSPECT RAW SCATTER）**。
- **取るべきアクション**：
 1. **平均化の厳禁**：これら2つのタイムスタンプを決して平均化（`15:10:23 UTC`）してはならない！平均化されたタイムスタンプは架空のアーティファクトである。
 2. 両方のヒットを跨ぐ60秒間の時間ウィンドウにわたる未加工の1秒生サンプルを点検する。
 3. 多くの場合、対流乱流の広がりを感知して局所的分散比を評価するFLOCが先に作動し、平均温度が尤度閾値を超えてドリフトした後に累積和シフトを評価するFocusが遅れて作動する。
 4. 両方のタイムスタンプを、単一の連続外乱ウィンドウの候補境界 `[15:10:14〜15:10:32 UTC]` として変化点テーブルに記録する。人間の監査人がその範囲内の物理的原因を評価する。

## 事例4：検出器は沈黙しているが、チャネルがフリーズしている場合

### 運用上の証拠
100%負荷での15分間の保持が終了した。FocusもFLOCも警報を1つも発しなかった。経験の浅い技術者は、運転が「極めて安定していた」と報告した。

生CSVファイルを検査したストレンジャーは、還流温度RTD-102が900秒間連続して正確に 45.000000°C を報告していたことを発見した。保持時間全体の計算標本分散は $σ² \equiv 0.000000 K²$ である。

### 診断上の判定
- **人間の分類**：**データ陳腐化／バッファフリーズ不正（STALE DATA / BUFFER FREEZE FRAUD）**。
- **物理的現実**：検出器が沈黙していたのは、その入力信号が死滅していたからである！変化点アルゴリズムは数値系列の偏差を評価する。系列が完全に平坦な定数であれば、アルゴリズムは偏差ゼロと認識して沈黙を守る。
- **取るべきアクション**：
 1. 検出器の沈黙はプロセスの安定性の証拠ではなく、テレメトリ障害の証拠である。
 2. 当該プラトーはデータ品質ゲートにおいて**不合格（FAIL）**と判定される。
 3. エッジゲートウェイの通信スレッドまたはADCドライバを診断・再起動し、負荷ステップ全体を最初からやり直さなければならない。

## 事例5：オフラインCPOPが保持開始直後に勾配変化をマークした場合

### 運用上の証拠
試験実行が完了し、ファイルがクローズされ、100%負荷保持時間に対してCPOPが実行された。CPOPは、15分間の保持の開始2分目に傾きの変化を特定した。指令有効電力は全期間を通じて一定であった。

### 診断上の判定
- **人間の分類**：**過渡解析ボックスの位置合わせ不良（TRANSIENT BOX MISALIGNMENT）**。
- **物理的根本原因**：オペレーターが定常状態評価ボックスの開始位置を早すぎる時点に設定した！保持時間の最初の2分間は、流体ループおよび重厚なステンレス容器外殻の物理的な熱的昇温過渡期（τ ≈ 45 秒）に相当していた。この2分間、流体温度は依然として漸近限界に向かって曲線を描いて上昇していた。CPOPは、曲線を描く過渡昇温から水平な定常プラトーへの遷移を正しく特定したのである。
- **取るべきアクション**：
 1. 「プラトーがCPOPで不合格になった」と主張してはならない。
 2. プロジェクトシート上の解析評価ボックスを、4分目以降（t ≥ 4τ）から開始するように調整する。
 3. 短縮されたウィンドウ `[4分目〜15分目]` に対してCPOPを再実行する。残りの11分間をCPOPがほぼゼロの傾き（|m| ≤ 0.001 K/s）を持つ単一の水平線としてフィッティングした場合、定常プラトーは数学的に検証されたことになる。
 4. ウィンドウ境界設定の工学的根拠として、熱時定数（τ = 45 秒）をレポートに明記せよ。

## 事例6：電力は平坦であるにもかかわらずCPOPが保持途中の勾配変化を検出した場合

### 運用上の証拠
クローズされたファイルにおいて、CPOPが15分間の保持を解析し、9分目に明確な勾配変化を配置した。有効電力は単一の水平勾配を示している（P_elec = 120.1 kW ± 0.1 kW）。体積流量もまた平坦である。しかし、温度の傾きは 0.000 K/s（水平）から +0.008 K/s（上向き上昇）へと遷移している。

### 診断上の判定
- **人間の分類**：**一次側施設冷却のドリフト（PRIMARY FACILITY COOLING DRIFT）**。
- **物理的根本原因**：電力および二次側流量が一定であったため、還流温度の上昇は負荷装置に起因するものではあり得ない。それは**一次側施設冷水ループ**によって引き起こされた：施設の中央チラープラントにおいて冷却塔ファンのステージ脱落が発生し、負荷装置に流入する二次側供給冷媒温度（T_in）が35.0°Cから37.2°Cへと上昇したのである。
- **取るべきアクション**：
 1. 供給温度チャネルを検証する：もし T_in が T_out の傾きを完全にトレースしていれば、負荷装置内部の温度上昇（ΔT = T_out - T_in）は10.04Kで完全に平坦を維持していたことになる。
 2. 温度上昇の原因を一次側施設供給ドリフトに帰属させる誠実な境界文言（外部機器 - CDUライン）を記述する。
 3. 負荷装置の熱容量は適合として証明され、施設側一次ループの安定性が制約事項として記録される。

## 事例7：CPOPはクリーンだが、熱の符号が誤っている場合

### 運用上の証拠
CPOPは、15分間の全負荷保持区間を欠陥のない単一の水平線（K = 0、分散ゼロ）としてフィッティングした。しかし、実測された供給温度は 45.1°C であり、還流温度は 35.0°C であった。

### 診断上の判定
- **人間の分類**：**水力配管の逆接続（REVERSED HYDRAULIC CONNECTION）**。
- **物理的現実**：試験クルーが供給ホースを負荷装置の還流ポートに接続し、還流ホースを供給ポートに接続してしまった！あるいはModbus変換テーブル内でソフトウェアチャネルのラベルが反転していた。
- **取るべきアクション**：
 1. アルゴリズムは「供給」や「還流」の物理的意味を理解しない。数値をフィッティングしているにすぎない。誤った符号を持つクリーンな勾配であっても、符号確認における致命的な不合格であることに変わりはない。
 2. 当該試験実行は即座に**不合格（FAIL）**となる。
 3. 最終報告スライドで符号を反転させるために、絶対値関数を適用することは断じて許されない！試験フロアでホース配管を正しく接続し直すかチャネルラベルを修正し、白日の下で試験を再実行せよ。

## 事例8：役員向けスライドのために単一の数値を要求された場合

### 運用上の証拠
正式レポートがまとめられる前に、プロジェクトマネージャーや役員が試験デスクにやって来て要求した：*「朝のスライド資料に貼り付けたいから、ラック3の変化点について1つの数値だけを教えてくれ。」*

手元には、`14:20:00` のステップ指令を示すオペレーターログ、`14:20:03` のFLOCヒット、`14:20:18` のFocusヒット、そして `14:23:45` のCPOP勾配遷移が存在している。

### 診断上の判定
- **エンジニアの対応**：
 1. **平均化された数値の提供を拒絶せよ**：$\frac{14:20:00 + 14:20:03 + 14:20:18 + 14:23:45}{4}$ を計算して、`14:21:01.5` という捏造されたタイムスタンプを渡してはならない！
 2. **監査可能な構造化表を提示せよ**：以下の表を提供する：
 - *指令ステップ時刻*：`14:20:00 UTC`
 - *オンライン検知ウィンドウ*：`14:20:03〜14:20:18 UTC`
 - *熱的整定完了時点（CPOP）*：`14:23:45 UTC`（整定時間 Δt = 225 秒）
 - *人間の分類*：**予期された負荷ステップ［合格］（EXPECTED LOAD STEP [PASS]）**
 3. 役員が表の提示を拒否した場合、スライドには人間の判定結果と指令時刻のみを記載する。捏造された中間数値を記載してはならない。

## まとめ：試験当日の標準手順

すべての試験キャンペーンにおいて、以下の時系列プロトコルを厳格に遵守せよ：

1. **加熱前**：改ざん不能な生CSVロギング経路を検証する。Focus、FLOC、およびCPOPの閾値がシート上で確定されていることを確認する。加熱前データ陳腐化プルーフテストを実施する（センサーを1つ抜線し、パイプラインが欠損ギャップを記録することを証明する）。
2. **アクティブウィンドウ中**：現場の生テレメトリストリームを監視する。オンライン候補ヒットが発生するごとに、オペレーターの指令ログと並べてそのタイムスタンプを直ちに記録する。事前に書面化された規則（注記または停止）を適用する。「ヒットが消えるかどうか確かめる」ために保持時間を延長することは決してあってはならない。
3. **ファイルクローズ後**：生CSVファイルの暗号学的ハッシュ（SHA-256）を生成する。定常保持ボックスに対してオフラインCPOPを実行する（初期の 4τ 昇温ウィンドウは除外する）。
4. **監査表の編纂**：すべての候補ヒットを指令ログのイベントと時系列で照合・整列させる。すべての行に対して人間の分類結果（*予期されたステップ*、*要点検／保持区間分割*、*影響なし*）をイニシャル署名する。
5. **5つの判定行の徹底**：検証された結果を速報の第1ページに転記する。「受入言明文」に署名するか、あるいは明確な「受入拒否言明文」を提出する。
